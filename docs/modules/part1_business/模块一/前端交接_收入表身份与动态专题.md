# 模块一前端交接：收入表身份与动态专题

接收方：前端任务（任务 08）。本文件定义模块一新增结果字段的展示要求；本任务不直接修改 `frontend/`，避免越过工作区责任边界。

## 新增数据

### 收入表身份

`revenue_total`、`revenue_totals[]`、`revenue_segments[]` 现在可能包含：

- `table_name`：模型从年报提取的原表名。
- `table_dimension`：产品、地区、渠道等拆分维度，用于区分标题相同但分类口径不同的表。
- `table_id`：同一报告内表格身份的稳定分组键；在标题之外会使用已匹配的表头文本区分同名异表。
- `fact_id`：事实项稳定查询键；收入行包含表身份，其他事实按模块类别和内容生成。
- `table_identity_status`：`report_title_text_verified`（原表名在已读取原文的 `table_title` 摘录中匹配到；只证明文字出现，不代表程序识别了整个表格结构）、`model_reported_title_unverified`（模型填写，尚未匹配原表名）或 `inferred_title_missing`（未取到表名、按其他字段推定）。
- `total_origin`：`reported_in_annual_report` 表示年报明确列出合计；`derived_from_reported_complete_segments` 表示原表没有合计行，程序按完整分项加总。后者必须展示为“程序计算合计”，不能伪装成年报披露值。
- `components`、`table_rows_complete`、`table_row_count`、`table_completeness_status`：程序计算合计的分项、条数和完整性状态。完整性起点是模型声明；程序另核对边界摘录和每条金额，UI 应说明这是基于模型完整度声明及程序逐行核对的加总。
- `evidence_id`：当前摘录和引用页的稳定查询键。
- `evidence[]`：分角色的原文支持项，每条含 `role`、`source_pages`、`evidence_quote`、`quote_verified` 和 `evidence_id`；收入行的 `row_value` 另有 `current_value_match` / `previous_value_match`，表示摘录中是否找到对应原始金额。收入表通常可见 `table_title`、`table_header`、`row_value`、`reported_yoy`、`management_explanation`。
- `calculation_ids`：期间变化、本期/上期占比和占比变化的稳定关联键；完整输入、公式与输出另保存在计算记录中。
- `calculation_evidence_status`：数值摘录是否匹配的状态。收入计算完整匹配要求原表标题、表头、对应本期/上期单位及金额均匹配；兼容旧结果会标为“只有摘录匹配，数字未独立核对”。
- `unit_match_current`、`unit_match_previous`、`unit_evidence_status`：单位字段是否能在带页码的单位原文证据中定位；旧输出允许退回检查表头引文。完整收入计算还须单位文本匹配，单位未定位时保留提取值但标记待复核。
- `current_share_denominator` / `previous_share_denominator`：程序选用的收入合计记录；用于展开占比的分母身份、期间和证据。
- `share_change_percentage_points`：本期占比减上期占比，单位为百分点；任一期未通过同口径和证据条件时为空。
- `reconciliation_to_reported_total`：程序计算的分项合计与同表年报明示总额的复核结果；差异必须并列展示，不能覆盖原文总额。`reported_total_unit_or_evidence_not_verified` 表示单位或合计证据未核实，暂不能比较。结构占比分母优先级为同维度年报合计、同表年报总合计、程序计算合计。
- `revenue_metric_bridges[]`：同一张总表内可核验的“营业总收入－营业收入”差额；只有两项表名、表头、单位、行值证据匹配后才生成，包含两项原始数值、程序差额、来源页、证据状态和稳定 `calculation_id`。模型解释若包含不一致的算术数字，结果会以程序复算说明替换。

`coverage_checks[]` 中 `key="revenue_structure"` 的收入结构项还会提供：

- `unit_evidence_review.current_records` / `previous_records`：本期/上期金额存在、但单位证据未通过定位的收入记录数。
- `shares_not_calculated.current_records` / `previous_records`：存在对应期间收入金额、但结构占比没有生成的分项数；具体原因看每条分项的 `current_share_note` / `previous_share_note`。

若单位证据缺失，收入结构覆盖状态会降为 `needs_review`，并在 `note` 说明待核数量和受影响的计算。不要把“有收入表引文”展示成“收入结构计算完整”。

展示要求：

1. 收入结构按 `table_id` / `table_name` 分组；表名为空时显示“表名未识别”，不得把来自不同表的同名行合成一张表。
2. 明确保留年报原始收入指标、单位、期间、报告范围和披露同比；“未计算”须保留程序给出的原因。
3. `report_title_text_verified` 可显示“标题文字匹配”，但不能简化显示为“表格已核验”；模型填写或推定标题应明确显示待核状态。
4. 若出现相同业务标签但不同 `table_id`，分开显示并允许对照查看，不将差异概括成错报。
5. `table_title` 匹配仅表示所报标题文字在来源摘录中出现；不能据此标记为“整表结构已自动核验”。`table_header` 和 `row_value` 应分别展示各自的匹配状态。
6. 展示收入占比时提供分子与所选分母的原表、拆分维度、原指标、期间、单位及出处入口。年报原文合计与程序按完整分项算出的合计必须分别标示。程序只在分子和分母的标题文字、表头、行值摘录均匹配且口径一致时计算；占比变化标成“百分点”，不可写作百分比增幅。
7. 展示收入差额/同比时同时展示 `calculation_evidence_status` 和 `unit_evidence_status`；未完整匹配或单位未定位时提示输入仍待复核。不要把算术成功展示为来源核验通过。

### 动态经营专题

`result.topics[]` 是第二阶段根据当前年报事实形成的公司特定专题。每项字段：

| 字段 | UI 用途 |
| --- | --- |
| `title` | 专题标题 |
| `question` | 专题回答的问题 |
| `observation` | 报告明确显示的变化/事实 |
| `analysis` | 有边界的分析 |
| `alternative_explanations` | 仍可能成立、尚未排除的解释 |
| `limitation` | 当前证据无法支持的判断 |
| `handoff` | 交由其他模块补核的具体事项 |
| `fact_id` | 专题事实的稳定查询键 |
| `source_pages`、`evidence_quote`、`quote_verified`、`evidence[]` | 页码、原文、多条证据角色和各自匹配状态 |
| `observation_numeric_evidence_status`、`unlocated_observation_numbers` | 观察字段里的数字是否能在所列来源页找到相同数值（金额换算按常见单位容差）；这是定位提醒，不等于含义、符号、口径已核验 |

`result.interpretation_review_items[]` 保存第二阶段返回的行业/战略分析无法与第一阶段事实名称对应，或同名条目有歧义的内容。字段含 `section`、`label`、`analysis`、`limitation`、`reason`、`status`。需在“待映射复核”区域保留这些解释原文及原因，不能将其混入已带出处的行业/战略事实，也不能直接丢弃。对应 `analysis_review_status` 应为“存在待复核内容”。

展示要求：

- 按模型产生的专题顺序全部展示，不重命名为固定的“六大分析模块”，不截掉解释或限制。
- 原文、公司解释、模型分析、替代解释和限制用不同标签/层级呈现，来源引用可点击定位 PDF 页。
- `evidence[]` 每条分别呈现角色和核验状态；不可把 `quote_verified` 当作数字已与具体表格行列相符或因果结论已被证实。
- `numeric_magnitudes_need_review` 时列出未在引用页定位的数字，提示补证或修正；不得把“数字未定位”直接说成事实错误，也不得把数字找到就说成整条结论正确。
- 没有专题时隐藏该卡组，不显示“分析失败”或空白占位。
- 已有业务画像、行业、战略、风险、收入及后续问题字段全部继续保留；动态专题不能替代或吞掉这些兼容字段。
- 将 `table_id`、`evidence_id` 保留在结果与导出数据中供核对，但通常不向普通用户展示哈希字符串。
