## 工作协议

### 1. 先施工单，后改代码

每个批次开始时，必须先新增或冻结一份独立的 `Bn-*.md` 施工单。施工单至少包含：

1. 批次目标和用户可观察结果。
2. 本批范围、明确不做的事和依赖项。
3. 计划新增、修改、删除、保留兼容的文件。
4. 接口、事件和数据结构契约。
5. 验收命令、预期结果和必须显现的失败条件。
6. 回滚方式、旧接口保护线和风险。
7. 最终证据表、原目标兑现表、独立信源状态和待拍板事项。

没有施工单，不得开始该批生产代码修改。施工过程中若范围变化，先更新施工单并说明原因，再继续实施。

### 2. 每批收工必须对原目标结账

收工表只能使用以下状态：

- `达标`：原目标和验收证据都满足。
- `未达标`：明确列出缺口、影响和下一批承接位置。
- `口径已放宽`：写明放宽理由、放宽人和替代验收方式。
- `已取消`：写明取消依据，不能只写“暂时不做”。

“本批测试全绿”只能证明没有发现新增回归，不能替代原目标核验。

### 3. 兼容线

- B1 到 B4 期间，旧入口 `/api/prefill`、`/api/analyze`、`/api/announcement`、`/api/ask`、`/api/search` 必须继续可用，直到新入口有等价测试并完成迁移。
- 旧 `agent/webui.py` 最终只保留启动兼容职责，不再承载 HTML、CSS、业务路由和流水线实现。
- CLI 入口的行为不属于本重构的删除范围。拆模块时优先保留现有函数名或提供明确导入转发。

### 4. 证据线

每批至少保留：

- 实际执行的命令和退出结果。
- 相关测试或检查的原始摘要。
- 接口或事件样例，包含 `run_id` 和 `seq`。
- 失败注入或反向检查结果，证明验收门不是恒真。
- Git diff 范围，确认没有越界修改。

外部独立结论若存在，应由该来源直接写入项目决策档。没有外部来源时，记录只读命令的原始输出，并明确写“独立信源：缺失”。

## 口径优先级

发生冲突时按以下顺序裁决：

1. 已冻结的本重构总方案和当前批次施工单。
2. 项目既有决策档中的用户已拍板口径。
3. 代码仓内可执行的测试和原始证据。
4. 实现便利性。

若实现过程中发现总方案有误，先记录问题、影响和替代方案，再更新文档和施工单，不允许静默偏离。
