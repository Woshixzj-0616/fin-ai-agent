# 金融投研智能体 · 重构方案

> 版本：2026-10-11
> 状态：总方案已冻结，作为 B0-B7 的核对基线。
> 范围：运行架构、Web API、实时执行轨迹、前端工作台、模块拆分、安全与质量门。
> 非目标：重写财务算法；改变“证据可追溯、数值由本地确定性代码裁决”的核心口径；删除现有 CLI；在未完成等价验证前替换旧接口。

## 一、重构结论

这次重构不是“把大文件拆小”，而是把系统从单体演示页面升级为可并发、可恢复、可实时观察、可长期维护的投研工作台。

核心目标有五个：

1. 一次分析是一个有身份、有状态、可查询、可取消的 `run`。
2. 前后端之间传输真实执行事件，刷新后仍能恢复，不再用定时器伪造进度。
3. 每个会话只访问自己的材料和结果，彻底移除 `LAST_FACTS`、`LAST_DOCUMENT_TEXTS` 这类跨会话全局状态。
4. 前端从后端源码中独立出来，形成任务输入、实时轨迹、证据结果、报告和有限问答的工作台。
5. 大模块按“变化的理由”拆分，并以契约测试、等价测试和兼容入口保证行为不回退。

不拆分模型思维链。模型内部可以有推理过程，但产品只展示经过校验的结构化计划摘要、工具调用、证据命中和本地裁决理由。原始 token 级思维链、系统提示词、密钥和未校验模型输出不进入事件流。

## 二、当前不足

### 2.1 运行层没有真正的任务模型

- `agent/webui.py` 当前在一次 HTTP 请求内同步执行完整流水线，请求结束前用户只能看到前端自行切换的阶段文案。
- `Run.event()` 已经写真实事件，但事件只落磁盘，未被实时广播。
- 一个进程内只有一把全局分析锁，所有用户串行等待。
- 缺少统一运行状态，无法可靠表达排队、执行、部分成功、失败、取消、过期。

### 2.2 会话隔离不足

- `LAST_FACTS` 和 `LAST_DOCUMENT_TEXTS` 是进程级共享变量。
- 后续 `/api/ask` 和 `/api/search` 只读取“最近一次分析”，多标签页或并发用户可能拿到别人的材料。
- 页面 `window.__last` 也只保证单标签页内的结果，不是可恢复的会话模型。

### 2.3 实时体验不足

- `setInterval` 每 2.5 秒切换预设阶段，与真实执行进度无关。
- 遇到抽取、页图渲染或模型调用停顿，用户不知道系统正在做什么。
- 执行轨迹只在最终响应返回后一次性渲染。
- 模型请求、响应校验、工具调用、回退和证据命中等关键步骤没有逐条到达前端。

### 2.4 前端和后端耦合

- `agent/webui.py` 同时承载 HTTP 服务、流水线、HTML、CSS 和 JavaScript。
- 真实页面被 Python 原始字符串包住，浏览器无法正常缓存和独立测试静态资源。
- `docs/app.js` 是与实时页面不同用途的静态快照组件，两套界面缺少共享设计契约。
- 当前页面以“最终结果大块替换”为主，加载、局部失败、重试和运行历史的状态表达不足。

### 2.5 模块边界和文件体量

当前主要体量基线：

| 文件 | 字节数 | 行数 | 主要问题 |
| --- | ---: | ---: | --- |
| `agent/webui.py` | 75,117 | 1,551 | HTTP、业务编排、HTML、CSS、JS 全混在一起 |
| `agent/extract.py` | 51,944 | 957 | 多报告类型和多抽取策略集中在一个模块 |
| `agent/llm_check.py` | 46,141 | 770 | 模型客户端、提示、循环、校验和回退耦合 |
| `agent/tools.py` | 25,954 | 528 | 工具规格、证据、计算、比较与调度混装 |
| `agent/materials.py` | 24,811 | 494 | 材料登记、运行归档、历史管理混装 |
| `agent/finance.py` | 27,602 | 487 | 指标和信号逻辑仍可继续按变化原因细分 |
| `agent/qa.py` | 18,588 | 409 | 问答逻辑可接受，但仍需接入 run 级会话数据 |
| `docs/app.js` | 33,628 | 670 | 静态快照前端单文件偏大 |

约 400 行是软阈值，不是机械拆分线。只有当一个文件同时承担多个独立变化原因，且拆分能降低共享状态、测试复杂度或回归风险时才拆。

### 2.6 安全边界不足

- 限流直接信任客户端提交的第一个 `X-Forwarded-For`，可被伪造。
- 上传校验主要依赖表单和文件扩展名，缺少 PDF 魔数、内容解析和资源上限的统一边界。
- 运行结果没有会话所有者检查。
- 缺少统一的活动运行数、排队上限、超时、取消和过期清理。
- 没有 CI 质量门，重构期间容易把“本地跑过一次”误当成长期约束。

### 2.7 模型能力边界表达不统一

现有设计正确坚持“模型拆句、工具取证据、Python 裁决”。重构后需要把这条边界落实到事件契约：

- 模型请求开始和结束可见。
- Schema 校验是否通过可见。
- 工具名、参数摘要、结果摘要和耗时可见。
- 结构化计划摘要可见。
- 缺少证据、工具失败和模型回退可见。
- 原始思维链不可见，也不用于生成最终审计结论。

## 三、智能旅行方法论的适用性

### 3.1 可以套用的部分

- 单次任务有明确的运行身份、状态机、步骤事件和终态。
- 前端以“正在发生什么”为中心，而不是只展示输入和最终报告。
- 任务恢复、取消、历史查询和错误重试都由统一运行层负责。
- 每个批次有独立施工单，先冻结边界，再实现和验收。
- 真实事件优先，不用模拟进度替代系统状态。
- 运行结果和过程证据分层，任务结束后仍能回看。

### 3.2 不能照搬的部分

- 旅行任务的路线、天气和地点具有连续空间关系；金融任务的核心是文档坐标、期间、单位、口径和证据链。
- 旅行可以接受较多概率式推荐；金融结论必须能落到页码、坐标、公式和输入指纹。
- 旅行编排更强调体验连续性；金融编排必须给确定性计算和证据门控更高优先级。
- 不能把“多 Agent 对话热闹”当成能力，金融系统的可信度来自可复现的本地裁决。

因此这里借的是运行时、事件流、工作台和批次治理，不照搬旅行领域的数据模型或决策方式。

## 四、目标原则

1. 单一运行真源：运行状态只由服务端 `RunManager` 维护，前端不推断。
2. 单一事件契约：实时 SSE、磁盘事件和最终轨迹共用同一事件结构。
3. 单一会话边界：每个 run 明确归属一个 session，所有结果查询都检查所有权。
4. 单一证据链：每项数值结论继续指向 evidence、页码、坐标、文件和 SHA-256。
5. 模型无裁决权：模型只拆句、规划受控工具调用或生成结构化候选，最终判定由本地证据与 Decimal 规则完成。
6. 兼容迁移：新入口先并存，旧入口通过适配层保留，等价验证完成后再退役。
7. 前端原生实现：继续使用 HTML、CSS、原生 JavaScript ES Modules，不引入 React 或 Vue，不扩大构建链。
8. 小步可回滚：每批只改一个主要变化面，保留上一批的可执行入口。

### 5.2 兼容策略

- 每个被拆模块先建立“旧导入名仍可调用”的兼容测试，再移动实现。

## 六、运行时设计

### 6.1 Run 生命周期

```text
queued -> running -> succeeded
                 -> partial_failed
                 -> failed
                 -> cancelled
                 -> expired
```

- `queued`：请求已受理，等待执行槽位。
- `running`：至少一个工作流步骤已开始。
- `succeeded`：全部核心步骤完成。
- `partial_failed`：有可展示结果，但部分材料、模型或报告步骤失败。
- `failed`：没有形成可用结果。
- `cancelled`：用户或系统取消，保留已发生事件。
- `expired`：超过结果保留期，只保留摘要或按策略清理。

### 6.2 RunManager 职责

- 创建 `run_id`，绑定 `session_id`、任务类型和输入摘要。
- 维护状态、开始时间、结束时间、当前阶段和错误摘要。
- 分配有限工作槽位，支持排队、取消和超时。
- 为每个 run 创建隔离目录，不再让并发运行共同写 `results/events.jsonl`。
- 完成后再原子发布最新结果和历史归档。
- 保存重放游标和数据，支持 SSE 断线续传。

### 6.3 EventBus 职责

- 接收运行事件，分配单调递增 `seq`。
- 同步保存事件，保证文件记录可恢复。
- 向所有订阅者广播；慢客户端有独立队列上限。
- 支持从 `Last-Event-ID` 后的第一条开始重放。
- 发送心跳，避免代理层关闭空闲连接。
- 断开只影响订阅，不取消正在执行的运行。

### 6.4 Session 设计

- 服务端签发不可猜的 `session_id`，通过 `HttpOnly`、`SameSite=Lax` Cookie 保存。
- run 记录包含属主 session，所有读取、追问、取消均检查属主。
- 本地单用户模式仍使用同一模型，避免开发路径和线上路径分叉。
- 会话过期只影响访问，不改变已产生证据的 SHA-256。

## 七、事件契约

所有实时事件、落盘事件和最终轨迹使用同一基础结构：

```json
{
  "run_id": "20261011_200000_ab12cd34",
  "seq": 12,
  "timestamp": "2026-10-11T20:00:03.125+08:00",
  "phase": "extraction",
  "event_type": "evidence.found",
  "actor": "parser",
  "title": "找到营业收入证据",
  "summary": "第 12 页命中，值待本地单位归一化",
  "status": "completed",
  "duration_ms": 84,
  "evidence_ids": ["ev_0012"],
  "payload": {}
}
```

### 7.1 事件阶段

| phase | 含义 |
| --- | --- |
| `run` | 创建、排队、开始、取消、终态 |
| `identity` | PDF 魔数、代码、公司、年度、期间 |
| `extraction` | 文本、表格、OCR、字段和证据 |
| `validation` | 单位和口径校验、缺值、冲突 |
| `model` | 请求、响应、Schema、结构化计划摘要、回退 |
| `tools` | 工具调用开始、结果、错误和预算 |
| `calculation` | 公式、操作数、结果和容差 |
| `claim` | 主张门控、裁决、需人工复核 |
| `report` | 报告生成、引用检查和导出 |
| `system` | 心跳、限流、取消和清理 |

### 7.2 关键事件

- `run.created`、`run.started`、`run.completed`、`run.failed`、`run.cancelled`
- `pdf.identity`
- `extraction.started`、`extraction.page`、`extraction.field`、`evidence.found`
- `validation.warning`、`validation.conflict`
- `model.request.started`、`model.response.received`、`model.response.validated`
- `model.plan.summary`
- `tool.call.started`、`tool.call.completed`、`tool.call.failed`
- `claim.gate`、`claim.decided`
- `report.ready`
- `run.fallback`、`run.error`

### 7.3 思维链边界

允许展示：

- 模型收到的任务类型、句数、工具预算等摘要。
- 经 Schema 校验的 `goal`、`next_action`、`reason_code`、`evidence_ids`。
- 工具调用的名称、参数摘要、结果摘要和耗时。
- 本地门控为什么放行、拒绝或转人工复核。

禁止展示：

- token 级 chain-of-thought。
- 系统提示词、密钥、完整供应商响应正文和内部调试字段。
- 模型未经验证的自由文本“理由”直接作为结论。
- 用户材料中不应公开的原文，除非它在当前运行证据卡片中按权限展示。

`model.plan.summary` 不是“补写一段思维链”，而是模型已经输出的结构化动作理由。它必须经过白名单字段过滤和长度限制。

## 八、HTTP 与 SSE 契约

### 8.1 新接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/runs` | 创建分析运行，返回 `run_id` 和状态 |
| `GET` | `/api/runs/{run_id}/events` | SSE 实时事件，支持 `Last-Event-ID` |
| `GET` | `/api/runs/{run_id}` | 查询状态、阶段、结果摘要和终态 |
| `POST` | `/api/runs/{run_id}/cancel` | 请求取消，返回实际状态 |
| `GET` | `/api/runs` | 当前会话的运行列表 |
| `POST` | `/api/runs/{run_id}/ask` | 只基于该 run 证据的受限问答 |
| `POST` | `/api/runs/{run_id}/search` | 只检索该 run 的页文本 |

创建运行后立即返回，不等待流水线完成：

```json
{
  "run_id": "20261011_200000_ab12cd34",
  "status": "queued",
  "events_url": "/api/runs/20261011_200000_ab12cd34/events",
  "poll_url": "/api/runs/20261011_200000_ab12cd34"
}
```

SSE 帧示例：

```text
id: 12
event: evidence.found
data: {"run_id":"...","seq":12,"phase":"extraction",...}

```

### 8.2 兼容接口

以下旧入口在迁移期保留：

- `POST /api/prefill`
- `POST /api/analyze`
- `POST /api/announcement`
- `POST /api/ask`
- `POST /api/search`

兼容策略：

1. 旧入口内部创建同一个新 run，但不要求客户端理解 SSE。
2. 旧入口等待终态后返回原 JSON 顶层结构。
3. `/api/ask` 和 `/api/search` 在缺少 `run_id` 时只允许访问当前 session 最近一次 run。
4. 兼容测试固定一份典型响应快照，前端迁移后仍验证旧字段未消失。
5. B7 只有在所有内部调用方迁移完成后才允许评估删除旧入口，默认不删除。

### 8.3 错误结构

新接口统一使用：

```json
{
  "error": {
    "code": "RUN_NOT_FOUND",
    "message": "运行不存在或无权访问",
    "retryable": false
  }
}
```

对外错误不返回堆栈、路径、密钥或供应商原始响应。详细错误只写运行日志。

## 九、前端工作台设计

### 9.1 目标界面

桌面端采用两栏工作台：

- 左侧为固定宽度运行栏，展示当前会话的运行列表、状态、任务类型和时间。
- 右侧为主工作区，顶部是任务输入，下面依次是当前阶段、实时执行轨迹、结果视图和报告。
- 运行栏在窄屏折叠为顶部状态条和抽屉，主工作区单列显示。

不使用营销式首页。打开即进入可用任务工作台。

### 9.2 核心区域

1. 输入区：PDF 拖放、身份修正、任务类型、比较材料、草稿核查、OCR 开关。
2. 阶段条：反映服务端真实状态；无法计算百分比时只显示确定阶段，不伪造百分比。
3. 实时轨迹：按 phase 分组，事件到达即追加。默认显示标题、状态、耗时和摘要，展开后显示白名单 payload 与证据链接。
4. 证据区：指标表、公告字段、页码、坐标、单位、口径和问题标签。
5. 裁决区：主张状态、本地规则结果、需要人工复核的原因。
6. 报告区：Markdown、导出、引用检查结果。
7. 追问区：仅针对当前 `run_id` 提问或检索，并显示所用证据。

### 9.3 实时交互规则

- `POST /api/runs` 成功后立即显示运行卡片并订阅 SSE。
- `Last-Event-ID` 由前端保存，网络恢复后从断点续传。
- 收到终态后关闭 SSE，再拉取完整结果。
- 局部结果先显示，不等待整条流水线完成。
- 页面刷新后根据 `run_id` 恢复状态和轨迹。
- 取消按钮必须显示“取消请求已发送”，最终以服务端事件为准。
- 任何错误都显示发生阶段和可重试动作，不把用户送回空白页。

### 9.4 视觉和可访问性

- 使用中性工作台底色、蓝绿作为正常状态、琥珀色作为警告、红色作为失败；避免单一色系和大面积渐变。
- 卡片圆角不超过 8px。只有事件项、证据项和模态框使用卡片边界。
- 使用 Lucide 风格一致图标或现有图标方案，图标按钮有 tooltip 和可访问名称。
- 事件标题、状态和摘要必须在桌面与手机宽度下不重叠、不遮挡。
- 颜色不是唯一状态信号，必须同时有文本或图标。
- 键盘可操作：任务提交、取消、轨迹展开、证据跳转和导出都有清晰焦点态。

### 9.5 前端文件拆分

- `tokens.css` 定义颜色、间距、字体、阴影和状态语义。
- `layout.css` 只负责工作台骨架和响应式网格。
- `components.css` 只负责控件、事件卡、证据 chip、表格和状态标签。
- `stream.js` 负责 SSE、重连、心跳和 `Last-Event-ID`。
- `run-state.js` 是前端唯一状态容器，避免页面各区域各自猜状态。
- `views/*.js` 只渲染任务、轨迹和结果，不直接发请求。
- `api.js` 是唯一 HTTP 客户端入口。

## 十、模块拆分原则

### 10.1 extraction

先冻结现有 `extract_material()` 对外行为，再按报告结构和变化原因拆：

- `metrics.py`：指标目录、别名、单位和共用匹配规则。
- `annual.py`：年度摘要表主路径。
- `income_statement.py`：利润表和营业总收入补取。
- `merge.py`：证据合并、去重、冲突和来源选择。
- `__init__.py`：只导出兼容的 `extract_material()` 和必要类型。

拆分验收以同一批夹具的 evidence JSON 为核心，要求 evidence 数量、ID、页码、坐标、值、单位和 issue 完全等价，除非施工单明确批准差异。

### 10.2 audit 和 tools

- `schema.py`：主张输入输出 Schema。
- `prompt.py`：提示模板和版本标识。
- `client.py`：模型 HTTP、流式、重试和错误。
- `grounding.py`：句子与证据接地。
- `claim_check.py`：双轨裁决和人工复核状态。
- `report.py`：报告生成和引用检查。
- `tools/specs.py`：工具声明单一真源。
- `tools/evidence.py`、`compute.py`、`compare.py`：工具实现。
- `tools/dispatch.py`：工具调度、预算和事件记录。

`tools.py` 和 `llm_check.py` 作为兼容门面保留，调用方先不一次性改 import。

### 10.3 不允许的拆分方式

- 不按“每 300 行一个文件”机械切。
- 不复制一份旧逻辑到新文件后让两套同时维护。
- 不在没有等价测试和回滚点前一次性改全部 import。
- 不把运行状态藏在模块级变量中换个名字继续使用。

## 十四、回滚与风险

- B0：删除新增文档即可回滚，不影响运行。
- B1：保留旧 `Run` 和旧入口，关闭新 RunManager 接线即可回退。
- B2：新 API 与旧 API 并存，路由开关可退回旧处理函数。
- B3/B4：保留旧页面入口，前端资产可回退到兼容页。
- B5/B6：旧模块作为门面，不删除实现调用方，可按文件回滚。
- B7：CI 和退役分批提交，旧入口删除必须单独可回滚。

主要风险：

1. 竞赛前重构范围过大。缓解：B5-B7 放到赛后。
2. SSE 长连接与现有 ThreadingHTTPServer 的兼容。缓解：先做最小压力测试，必要时限定连接数和超时。
3. 事件 Schema 频繁变化。缓解：B1 冻结 v1，新增字段向后兼容，删除字段需版本升级。
4. 模块拆分产生隐性导入分叉。缓解：兼容门面、导入图测试和结构化输出等价测试。
5. 前端视觉改动压过可信信息。缓解：证据、页码和冲突状态优先，动效和第二视觉元素后置。
